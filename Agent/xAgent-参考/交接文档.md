### 分层的硬约束

`core/` **不许** import `textual`、`rich`、`tkinter`、`PyQt5/6`、`PySide2/6`、`curses`、`wx`。
`tui/` **不许** import `subprocess`、`urllib`、`http.client`、`socket`、`shutil`，也不许自己 `open()` 文件。

这两条不是嘴上说说，`_test_layers.py` 会用 AST 解析每个 py 文件的 import 来强制检查。

### 为什么这样设计

作业要求「为未来开发其他界面版本做好准备（Web、Desktop）」。

现在的做法是：`core.Agent` 暴露 6 个可选回调，界面层订阅这些回调来显示过程。换界面时，建个 `Agent`、挂上回调、调 `agent.ask(text)` 就行，业务代码一行不用改。

6 个回调在 `interfaces/README.md` 里有完整签名说明：

```python
agent.on_assistant_start()                  # 一轮开始
agent.on_assistant_delta(text)              # 流式收到一段正文
agent.on_assistant_end(text, tool_calls)    # 正文结束，带工具调用
agent.on_tool_start(name, arguments)        # 准备执行工具
agent.on_tool_end(name, result, error)      # 工具执行完
agent.on_error(message)                     # 出错
```

## 六、本轮修掉的两个 bug（别再踩）

### Bug 1：中文占位符塞进 HTTP 头导致崩溃

**现象**：

```
UnicodeEncodeError: 'latin-1' codec can't encode characters in position 7-11: ordinal not in range(256)
error = UnicodeEncodeError('latin-1', 'Bearer 你的密钥', 7, 11, ...)
```

**原因**：`config.example.ini` 模板里 `api_key = 你的密钥`，用户直接复制成 `config.ini` 没改。这串中文被当成真密钥拼进 `Authorization` 头，而 HTTP 头只能装 latin-1。

**修复**：`core/config.py` 加了 `_clean_key()`：

```python
def _clean_key(api_key):
    key = (api_key or "").strip().strip('"').strip("'")
    if not key:
        return ""
    try:
        key.encode("ascii")
    except UnicodeEncodeError:
        return ""          # 非 ASCII 一律当没填
    if key.lower() in ("your-key", "your_key", "placeholder", "xxx", "none", "null"):
        return ""
    return key
```

### Bug 2：`启动.bat` 一闪就消失

**原因**：bat 文件是 UTF-8 编码，但系统代码页是 936（GBK）。cmd 按 GBK 解 UTF-8 字节，中文全乱码，而且乱码把换行符吃掉了：

```
echo 绋嬪簭宸查€€鍑恒€?pause     ← pause 粘到 echo 后面，不执行
```

`pause` 没执行，程序一退出窗口就关了。

**修复**：bat 内容全改英文，不用 chcp：

```bat
@echo off
cd /d D:\LLM\Agent\xAgent
set "PYTHONIOENCODING=utf-8"
set "PYTHONUTF8=1"
echo Starting xAgent...
echo.
python main.py
echo.
echo Exited.
pause
```

**教训**：在这台机器上写 `.bat`，要么全 ASCII，要么用 GBK 编码保存，别用 UTF-8。

## 八、代码里几个值得知道的细节

### 1. 流式 tool_calls 必须按 index 归并

模型下发的 tool_calls 是分片的，可能一次只给 id、下一次只给 arguments 的一小段：

```
第1片: {"index":0, "id":"call_x", "function":{"name":"isLeapYear","arguments":""}}
第2片: {"index":0, "function":{"arguments":"{\"year\":"}}
第3片: {"index":0, "function":{"arguments":" 1900}"}}
```

`core/llm/client.py` 的 `ToolCallBuffer` 负责攒齐。测试里专门验证了这个。

### 2. 出错要整轮回滚

`core/agent.py` 的 `ask()` 失败时执行 `del self.history[mark:]`，删掉**这一轮追加的所有消息**，而不是只删最后一条。

原因：如果只 `pop()` 最后一条，会留下有 `tool_calls` 却没有对应 `tool` 响应的 assistant 消息，下一轮请求会被服务端直接拒绝。

### 3. 界面网络请求必须走工作线程

`tui/app.py`：

```python
self.run_worker(lambda: self._agent.ask(text), thread=True, exclusive=True)
```

`agent.ask()` 是阻塞的（同步 urllib）。直接在主线程调用会让整个界面卡死。

### 4. 流式片段要按行聚合

`tui/widgets/chat_log.py` 的 `push_delta()`：RichLog 每次 `write()` 就是新的一行，不能来一个片段写一行，否则会变成一个词一行。这里攒到 `\n` 才写。

### 5. `getDate` 为什么必须调命令

Windows 自带的 `date` 是**修改日期**的命令，不是取时间：

```
> cmd /c "date +%Y-%m-%d"
The system cannot accept the date entered.
Enter the new date: (yy-mm-dd)     ← 它在等用户输入
```

所以 `datetime_tools.find_date()` 会在 PATH 和 Git 常见安装位置里找真正的 `date.exe`（本机命中 `D:\Git\usr\bin\date.exe`），找不到才退回 `cmd /c date /t` + `time /t`。

**这是老师作业的要求**（「应该采用调用本地 date 命令的方式，而不是编写 python 代码」），不是随意选择。
