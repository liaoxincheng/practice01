# Practice02 实测流程

目标：亲手验证 `getDate` 和 `isLeapYear` 两个 function call 工具真的被模型调用，而不是模型自己在编。

---

## 一、先看清一件事：两个工具的验证重点不一样

| 工具 | 实现方式 | 你要验证什么 |
|------|----------|--------------|
| `getDate` | 调本地 `date` 命令 | 返回的时间和你电脑右下角时间一致 |
| `isLeapYear` | 纯 Python 计算 | 世纪年陷阱（1900/2000/2100）算得对 |

`getDate` 好验证——时间对不对，你一眼就知道。
`isLeapYear` 麻烦一点——因为模型自己"心算"也能答对，所以你要盯的不是它答得对不对，而是**它有没有真的调用工具**。

判断依据就是屏幕上这行 `[tool]` 日志：

```
[tool] isLeapYear({"year": 1900})
[tool] -> 1900 年不是闰年，2 月有 28 天，全年 365 天。
1900年不是闰年，2月有28天，全年共有365天。
```

第一行是模型请求调工具，第二行是工具真跑出来的结果，第三行才是模型的话。
**如果只有第三行、没有前两行**，说明模型没调工具、纯靠嘴答的，这次验证无效，换个问法重问。

## 四、验证清单（按顺序敲）

### 第 1 组：getDate 基本功能

```
现在几点了？
```

预期：
```
[tool] getDate({"format": "%H:%M:%S"})
[tool] -> 17:25:40
现在是17:25:40。
```

**验收标准**：`[tool] ->` 后面的时间和任务栏时钟对一下，差几秒算正常（中间有推理耗时）。

### 第 2 组：getDate 换格式

```
今天几号？星期几？
```

预期模型会传 `%Y-%m-%d %A` 这类格式：
```
[tool] getDate({"format": "%Y-%m-%d %A"})
[tool] -> 2026-10-19 Monday
今天是2026年10月19日，星期一。
```

**验收标准**：日期、星期和实际一致。这一组顺带验证了 `format` 参数透传。

### 第 3 组：isLeapYear 普通年份

```
2024年是闰年吗？
```

预期：
```
[tool] isLeapYear({"year": 2024})
[tool] -> 2024 年是闰年，2 月有 29 天，全年 366 天。
```

### 第 4 组：isLeapYear 世纪年陷阱 ★重点

```
闰年是不是4年一次？给我算算 1900、2000、2100。
```

预期（一轮里并发 3 个 tool_call）：
```
[tool] isLeapYear({"year": 1900})
[tool] -> 1900 年不是闰年，2 月有 28 天，全年 365 天。
[tool] isLeapYear({"year": 2000})
[tool] -> 2000 年是闰年，2 月有 29 天，全年 366 天。
[tool] isLeapYear({"year": 2100})
[tool] -> 2100 年不是闰年，2 月有 28 天，全年 365 天。
```

**验收标准**：这是整段代码最容易错的地方。
- 1900 → 不是闰年（能被 4 和 100 整除，但不能被 400 整除）
- 2000 → 是闰年（能被 400 整除）
- 2100 → 不是闰年

如果 1900 被答成闰年，说明计算逻辑错了——但当前代码已用 15 个边界用例测过，理论上不会错。

### 第 5 组：跨工具链式调用

```
先用工具查一下现在是哪一年，再判断那一年是不是闰年。
```

预期：
```
[tool] getDate({"format": "%Y"})
[tool] -> 2026
[tool] isLeapYear({"year": 2026})
[tool] -> 2026 年不是闰年，2 月有 28 天，全年 365 天。
```

**验收标准**：先 `getDate` 拿年份，再 `isLeapYear` 判断，两个工具串起来了。

## 五、特别观察点："今年"会被自动纠正

```
今年是闰年吗？
```

预期：
```
[tool] isLeapYear({"year": 2026})
[tool] -> 2026 年不是闰年，2 月有 28 天，全年 365 天。
```

**注意看 `year` 的值是 2026，不是 2024。**

这是踩过的坑：`qwen3-vl:4b-instruct` 面对"今年"这个词，会凭训练先验直接填 `2024`（因为 2024 是最近的闰年，训练数据里出现得多）。改工具描述没用，最后在代码里做了兜底——你这句输入里如果没有任何三位/四位数字，就用本机当前年份覆盖模型猜的值。

验证方法：问"今年是闰年吗"，看日志里是不是 `2026`。如果你看到 `2024`，说明兜底没生效。

## 六、退出

三种方式都行：
- 敲 `Ctrl+C`
- 敲 `Ctrl+Z` 再回车
- 直接关窗口

代码里捕获了 `KeyboardInterrupt` 和 `EOFError`，会干净退出，不抛异常栈。

**模型服务不会跟着退出**（`启动本地模型.bat` 里用 `start` 起的独立窗口）。要关的话：
```
taskkill /F /IM llm.exe
```

或者直接在任务管理器里结束 `llm.exe`。

## 七、排错

### 报 `连不上模型服务` 

会看到这样三行提示（不会甩异常栈）：
```
连不上模型服务 http://127.0.0.1:11437/v1
原因：[WinError 10061] 由于目标计算机积极拒绝，无法连接。
先确认服务已启动：netstat -ano | findstr :11437
```

检查端口：
```
netstat -ano | findstr ":11437"
```
没有 LISTENING 就手动按"方式 B 窗口 1"起服务。

### 报 `KeyError: 'base_url'`

`config.ini` 读不到或被改坏了。当前应该是：
```
base_url = http://127.0.0.1:11437/v1
model = qwen3-vl:4b-instruct
api_key =
```

注意：`chat.py` 是**按当前工作目录**找 `config.ini` 的，所以必须 `cd` 到 Practice02 再运行。

### 中文变乱码

没设 `PYTHONIOENCODING=utf-8`。补上：
```
set PYTHONIOENCODING=utf-8
```

### `[tool] ->` 返回的是 `周一 2026/10/19  17:26` 这种格式

这是走到了 Windows 自带 `date /t` 的兜底分支，没找到 Git 的 `date.exe`。检查：
```
dir D:\Git\usr\bin\date.exe
```
存在的话不该走到兜底。如果 Git 装在别处，改 `chat.py:57-62` 的 `DATE_EXE_FALLBACKS`。

> 注：这个兜底分支之前有编码 bug——返回的是 `鍛ㄤ竴 2026/10/19`（"周一"被按错误编码解码）。原因是 `subprocess.run(text=True)` 用系统默认编码解，而 cmd 输出的是 GBK 字节。现在 `run()` 改成先按 UTF-8 解、失败再按 GBK 解，已修复并实测通过。

### 模型答了但完全没有 `[tool]` 日志

两种情况：
1. 模型觉得不用调工具，直接答了 —— 换个更明确的问法，比如"请调用工具查"。
2. 模型不支持 function call —— 当前 `qwen3-vl:4b-instruct` 实测是支持的。

## 八、想自己改代码验证的话

`chat.py` 里三个位置最关键：

| 位置 | 作用 |
|------|------|
| `chat.py:19-54` | `TOOLS` 列表，工具声明 |
| `chat.py:111-113` | `is_leap()`，闰年核心逻辑，就一行 |
| `chat.py:131-141` | `normalize_args()`，"今年"兜底逻辑 |

想验证兜底逻辑是否必要，可以把 `normalize_args` 里那行 `args["year"] = int(get_date("+%Y"))` 注释掉，再问"今年是闰年吗"，你会看到模型填 `2024` 然后答错。
